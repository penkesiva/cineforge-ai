# Supabase (local Postgres)

CineForge uses the Supabase CLI local stack for Postgres. The app connects directly
with `DATABASE_URL`; it does not use the Supabase REST API, Auth or Storage in Phase 0.

## Lean local stack

`supabase/config.toml` disables everything except the database:
`api`, `studio`, `auth`, `storage`, `realtime`, `analytics`, `edge_runtime`,
`local_smtp` and the pooler are `enabled = false`.

Why: fewer containers, less RAM and disk (important on laptops), faster
`supabase start`, and nothing the Phase 0 app needs. Postgres listens on
**127.0.0.1:54322** (user `postgres`, password `postgres`, db `postgres`).

```bash
make db-start           # supabase start (no-op if running)
supabase status         # URLs and keys
make db-stop            # supabase stop (data kept in the Docker volume)
make db-reset           # DESTRUCTIVE: drop data, re-apply migrations + seed
psql postgresql://postgres:postgres@127.0.0.1:54322/postgres
```

## Enabling more services later

Flip the section in `supabase/config.toml` and restart (`supabase stop && supabase start`):

| Need | Section(s) |
|---|---|
| Studio UI (<http://127.0.0.1:54323>) | `[studio]` + `[api]` |
| Auth (PRD 2 tenancy) | `[auth]` + `[api]` |
| Storage (`STORAGE_BACKEND=supabase`) | `[storage]` + `[api]` |
| Realtime | `[realtime]` + `[api]` |

`config.toml` is integrator-owned; propose the change instead of editing it in a
workstream branch.

## Migrations and seed

- Migrations: `supabase/migrations/<timestamp>_<name>.sql`, applied in order.
  Append-only: create a new file with `supabase migration new <name>`, never edit an
  applied migration. Phase 0 schema is frozen (integrator only).
- Seed: `supabase/seed.sql`, generated by `scripts/generate_seed.py` (Workstream D)
  from `packages/configurations`. Applied after migrations on `supabase db reset`.
- CI applies the same files with `psql` to a plain `postgres:17` service
  (see `.github/workflows/ci.yml`), so migrations must not depend on Supabase-only
  roles or extensions unless CI is updated too.

## Switching to Supabase Cloud

Configuration only, no code changes:

```bash
DATABASE_URL=postgresql://postgres.<ref>:<password>@<region>.pooler.supabase.com:5432/postgres
DOCKER_DATABASE_URL=$DATABASE_URL     # containers use the same cloud URL
SUPABASE_URL=https://<ref>.supabase.co
SUPABASE_SERVICE_ROLE_KEY=<service role key>    # only in .env, never in Git
STORAGE_BACKEND=supabase                         # when Supabase Storage is wired up
```

Apply migrations to the cloud project with `supabase link --project-ref <ref>` then
`supabase db push`. Never point local tests at a production database.
